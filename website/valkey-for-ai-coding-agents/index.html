A local Valkey server for AI coding agents on Mac

Coding agents like Claude Code, Codex and Cursor work through the terminal. When your project needs Valkey (or Redis), the agent has to find a server, start it, get its URL and read its log when something breaks. Valkey.app's valkey-app command does all of that, with JSON output an agent can rely on.

Set up the command

Install Valkey.app, then click Settings › Command Line › Install CLI (or run the app's executable once: /Applications/Valkey.app/Contents/MacOS/Valkey app install-cli). The Homebrew cask links valkey-app for you. If the app isn't running, any command starts it in the background.

Everything is discoverable

An agent doesn't need this page. It can read the whole command reference as JSON:

valkey-app help --json          # every command, argument, option and example
valkey-app help create          # one command, as text

The CLI does everything the app's window does: servers, settings, ACL users, modules, versions and app settings. That's a rule in the project (AGENTS.md): anything added to the app is added to the CLI in the same change.

JSON output

Add --json to any command. Keys are stable and sorted, and optional keys are left out when they're not set (treat a missing key as null).

valkey-app list --json
valkey-app show myapp --json
valkey-app url myapp --json
# {
#   "url" : "valkey://127.0.0.1:6390"
# }

A server has id, name, version, port, state (running, stopping, stopped or failed), failure, modules, dataDirectory, configFile, logFile and its settings. The full list of shapes is in the CLI reference.

Create, start, debug

valkey-app create myapp --version 9.2.0 --port 6390 --json
valkey-app start myapp --json
valkey-app logs myapp -n 100 --filter error --json
valkey-app stats myapp --json
valkey-app cli myapp DBSIZE

start waits until the port accepts connections and stop waits until the process has exited, so the next command never races the server. Downloads (a new version or module) finish before the command returns. delete asks for confirmation on a terminal; agents must pass --yes, and the data directory stays on disk either way.

Exit codes and errors

CodeMeaning
0OK
1Failed (for example, the port is in use)
2Usage error (unknown command or option)
3Not found, or a name shared by several servers
4Valkey.app unreachable

With --json, errors print {"error": "…"}, and confirmation prompts go to stderr, so stdout stays parseable. Typos get a hint, such as Unknown option --prot. Did you mean --port?

Passwords stay hidden

Passwords never appear in output unless you pass --show-secrets. url shows the password as **** without it. cli hands the password to valkey-cli in an environment variable, never on the command line, and --password - reads a new password from stdin. An agent can do its work without a password ever landing in its transcript.

## Local Valkey

This project needs a local Valkey server (Redis-compatible). On macOS, use Valkey.app's `valkey-app` CLI:

- Check for it: `valkey-app show myapp --json` (exit code 3 means it doesn't exist yet).
- Create it once: `valkey-app create myapp --version 9.2.0 --port 6390`
- Start it: `valkey-app start myapp` (waits until it accepts connections).
- Connection URL: `valkey-app url myapp --json`. Use it as REDIS_URL; if a client only accepts
  redis://, keep the host and port and change the scheme.
- Debug: `valkey-app logs myapp -n 100 --json`, `valkey-app cli myapp <command>`.
- Don't use --show-secrets, don't delete servers, and don't run FLUSHALL unless asked.
- Full reference: `valkey-app help --json`.

Compared with Homebrew and Docker

An agent can drive brew services or docker run too. The difference is what it gets back. brew services manages one Valkey version and has no per-server settings or structured status. Docker has JSON (docker inspect), but needs Docker running, and the agent has to work out ports, volumes and image tags itself. valkey-app gives every server a name, a fixed port and a data directory, and answers in one JSON shape across every command.
